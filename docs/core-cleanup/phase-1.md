### Dependency and caller map

- `gplspec/All` combines `GeneralModels`, `SimpleModels`, mapping, the 1D matrix wrapper, spectral-element tools, preconditioner, spherical integrator and timer. `GeneralModels` includes `SimpleModels` and the 3D density construction/return, perturbation, 1D/3D model and gravity headers. `Core` exposes mapping, 1D matrix wrapper, preconditioner, integrator and timer. `Test` exposes general/simple models, the 3D matrix wrapper, radial tools and `testtools.h`; `Timer` exposes `Timer_Class.h`.
- Model constructors and return methods depend on radial mesh/discretization, shared utilities, `testtools.h`, and external PlanetaryModel/TomographyModels/Interpolation/GaussQuad/GSHTrans/FFTWpp/Eigen interfaces. Gravity routines depend on model headers, matrix wrappers, radial/shared utilities, Eigen iterative solvers and transform/quadrature dependencies. This is a header-level dependency map, not yet a proposed architecture.
- Representative named routines and tracked callers: `Density3D::SphericalHomogeneousPlanet` is called by `examples/clean_bench_1.cpp` and `_tutorials/homogeneous_sphere.md`; `Density3D::OneDimensionalPlanetFromFile` is called by `examples/clean_bench_2.cpp` and `_tutorials/tutorial2_prem.md`; `Density3D::SphericalThreeDimensionalPlanetFromFile` is called by `examples/clean_bench_6.cpp` and `_tutorials/tutorial3_tomo.md`. These constructors call `TestTools::EarthModel` internally (`Density_Model_Constructors.h`). `TestTools::PhobosRead` is called by `examples/phobos_gravity.cpp`, `examples/phobos_heterogeneous.cpp`, `examples/phobos_gravity_perturbation.cpp`, and `examples/OutputZiheng.cpp`. `Gravity_Tools::FindGravitationalPotential` is called by `examples/clean_bench_1.cpp`, `examples/clean_bench_2.cpp`, `examples/phobos_gravity.cpp`, and several tutorials; `FindGravitationalPotentialPerturbation` is called by `examples/clean_bench_10.cpp` and `examples/phobos_gravity_perturbation.cpp`. These are tracked callers, not a complete external-consumer inventory; confirm downstream users before retirement.

### Scientific boundaries and evidence classes

- A numerical element is a radial discretization interval with polynomial nodes/quadrature (`Radial_Tools.h`, `Spectral_Element_Tools.h`, `Model_Construction_Utilities.h`). A material/model layer is supplied by the input model and associated discontinuity/layer indices (`node_info` in `Radial_Tools.h`, `spherical_1D` in `Earth_General_Models_1D.h`). The current mesh invariant is stronger than mere separation: `Radial_Tools::node_info` divides each input-model layer into one or more elements, explicitly appends that layer's `UpperRadius` as the final element node (lines 134–155), records layer-boundary element indices, then builds the per-element quadrature nodes (lines 179–181). Therefore every input-model layer boundary is an element node, while additional element boundaries may occur inside a layer. The constructor maps each element to its model layer and samples it using that layer (`Earth_General_Models_1D.h`, including layer advancement at `IdxUpperRadius`). Preserve both this alignment invariant and the distinction between discretization and material boundaries; one-sided interface values require explicit later coverage.
- `tests/reference/*` are checked-in comparison inputs/expected products (CSV, serialized output, coefficient data or checksum manifest). The harness and runner sources under `tests/` generate candidate outputs in temporary or build-owned locations. `modeldata/*` are model inputs. `examples/` and `work/` produce/read scientific outputs. `benchfigures/*` are saved figures. No saved product is fresh evidence for the present base without rerunning its documented procedure.
- In `testremove`, the full potential programs and the sparse/dense spectral-element programs are separately implemented experiments, not demonstrated duplicates merely because they target the same physical problem. The current supported solver path and independent comparison status must be assessed before a later keep/remove decision.
