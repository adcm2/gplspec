## Stage 2A — scoped map and decisions

### Practical repository, build, and documentation candidates

The current CMake setup has several concrete simplification candidates, to be validated before changing them:

- CMake sets C++23 globally even though `gplspec` is an interface library. Candidate: express the minimum language level through the `gplspec` target's usage requirements so standalone and parent-project consumers receive it without changing unrelated targets.
- `CMAKE_MODULE_PATH` uses `CMAKE_SOURCE_DIR`, which points at the top-level consuming project when GPLSpec is included as a subproject. Candidate: make GPLSpec's `cmake/FindFFTW.cmake` lookup relative to `CMAKE_CURRENT_SOURCE_DIR`, retaining the same FFTW discovery behavior.
- `gplspec` already links its dependency targets transitively, while each example repeats several of those links. Candidate: make examples link through the supported `gplspec` target and verify all applications still configure and link.
- Top-level CMake requires OpenMP, while the tracked GPLSpec, example, and test sources inspected for Stage 2A show no OpenMP directives or API calls. Candidate: remove the unconditional requirement only after checking pinned dependency requirements and all supported build modes.
- Root CMake retains commented-out compiler, flags, dependency, target, and test setup. Candidate: remove only comments proven obsolete by current targets and documentation; retain explanatory provenance for pinned dependencies and the ODR patches.
- `api.md` and `api/api.md` are both tracked, with the latter a placeholder; `getting-started.md`, `benchmark.md`, `tutorials.md`, `_tutorials/`, and root/site pages overlap in navigation and user instructions. Candidate: identify one canonical location for each current build/API/benchmark instruction and update all incoming links before removing duplicate or stale text. Keep historical cleanup evidence and tutorial scientific explanations where still useful.

These are proposals, not Stage 2A code changes. Phase 2B/2C must record each actual change and validation state in `implementation_status.md`.
